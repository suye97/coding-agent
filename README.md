# 需求交付台

独立的 Electron 桌面应用。飞书收到完整需求后，自动完成方案设计、独立 Git worktree 开发、固定项目检查、必要的实际操作验证和同名分支推送。左侧展示任务队列，右侧持续展示真实的模型增量正文、方案、验证证据与交付提交。

## 技术栈与进程边界

- **Electron Main**：配置、SQLite、飞书长连接、任务状态机、Git worktree、检查和推送。
- **Electron Utility Process**：通过 Claude Agent SDK 执行设计、开发与验证；崩溃不会直接拖垮界面。
- **React Renderer**：只展示安全字段，通过受限 IPC 调用主进程；没有 Node.js 权限，也不读取密钥。
- **TypeScript / React / Vite**：桌面进程与界面代码使用 TypeScript，成熟业务核心保留现有 JavaScript 并通过声明文件接入类型系统。

## 环境与启动

需要 Windows、Node.js 24 或更高版本、Git，以及可访问的飞书和 Anthropic 兼容模型服务。

```powershell
npm install
npm run dev
```

生产构建与安装包：

```powershell
npm run build
npm run dist
```

如果 Windows 提示安装器以低完整性运行，不要重试或关闭安全软件。请把自己构建、或从可信来源获得的安装包放到正常的本地目录，再从资源管理器打开。隔离工作区里的 `release` 可能继承低完整性标签，不能直接用来运行安装器或做启动验收。

测试：

```powershell
npm test
npm run test:desktop
```

单元和业务回归测试使用临时 SQLite 数据库、替身 Agent、替身飞书渠道和真实 Git worktree。安装器验收使用 [smoke-installer.mjs](scripts/smoke-installer.mjs)，在干净的 Windows 测试账户、虚拟机或使用独立安装标识时运行，验证安装登记、快捷方式、沙箱启动和卸载；传入旧包还可验证升级。验收还启动安装包里的真实 Claude Agent SDK 和 CLI，用仅监听本机的模拟接口检查会话、流式输出和最终结果，不调用真实模型或飞书。临时安装目录本身不会隔离 Windows 安装身份。

## 首次配置

打开左下角的 **设置**：

1. **飞书渠道**：填写 App ID、App Secret、操作人 Open ID。数据目录可留空，默认位于应用用户数据目录下。完成模型和项目配置后再开启需求处理。
2. **模型**：填写 Anthropic 兼容 Base URL、模型名称和 API Key。API Key 留空表示保留原值。
3. **项目仓库**：选择本机 Git 工作仓库根目录，填写项目名、别名、基线分支和远程。项目名用于匹配飞书需求。

App Secret 和 API Key 使用 Electron `safeStorage` 调用操作系统加密能力后保存。Renderer 只能看到“已配置”，收不到密钥原文；密钥不会写入 SQLite、任务卡片、模型正文或应用日志。

飞书开放平台需要启用机器人、长连接、`im.message.receive_v1` 和新版卡片回传 `card.action.trigger`，并授予接收消息、读取消息资源、发送与更新消息所需权限。

## 提交需求

单聊或已配置群聊中发送：

```text
开发需求｜订单服务
需求正文：为订单列表增加状态筛选
```

缺陷修复使用 `修复缺陷｜订单服务` 或 `修复bug｜订单服务`。正文也可与项目名写在同一行。项目可识别且正文有效时直接进入设计，不需要人工确认方案。信息不足时才显示补充卡片。

任务创建独立分支和 worktree：新功能使用 `feature/<任务编号>_YYYYMMDD`，修复使用 `fix/<任务编号>_YYYYMMDD`。开发 Agent 只在任务 worktree 工作，本地提交由主程序复核。固定检查、操作证据和必要的人工变更审核全部通过后，主程序推送同名分支。

## 调度与输出

左侧按任务显示项目、阶段和摘要。选中任务后，右侧提供：

- **过程**：每次调用的实时模型正文、运行状态与安全调用信息。
- **方案**：实现范围、风险和验证计划。
- **验证**：固定项目检查结果和逐项实际操作证据。
- **交付**：任务分支、提交和实际变更摘要。

只保存每个任务最近 8 次有正文输出的调用，每次最多保留最后约 24,000 字符。私有推理、原始工具参数和输出、环境变量及凭据不会发送到 Renderer。

## 分层验证

纯代码、接口和命令行变更可以只使用固定项目检查。涉及用户界面或明确操作行为时，验证方案必须包含可执行步骤和预期结果。证据按以下顺序复用：

1. 项目自己的 `kind: operation` 自动化操作检查报告。
2. 开发 Agent 在同一待交付提交上产生的完整工具证据。
3. 独立验证 Agent 只补缺失步骤。

证据绑定提交、需求版本、方案版本、完整步骤和缺陷基线。推送失败后的重试复用有效证据；缺陷返工可复用同一基线的复现记录，但必须验证新提交。空提交、无增量差异的返工、过期证据和模型自述均不能通过交付门禁。

独立验证保留 10 分钟总时限、60 秒 SDK 协议启动时限、3 分钟无协议进展时限、3 分钟单步时限和 10 秒有界清理；整个验证阶段有 15 分钟预算。恢复已有会话时同样以首个协议事件结束启动计时，不依赖新的会话 ID。只有主程序接受下一步骤证据才重置单步计时。中断后按检查点继续，已完成步骤不重复采集。

对于有 npm 锁文件且直接依赖 Electron 的项目，操作验证预检会检查工作树内的 Electron 可执行文件，缺失时调用该版本的安装脚本补齐，并试启动确认版本；Windows 下必要时会从独立临时目录启动同一版本。不使用已安装的需求交付台替代目标应用。预检失败不会启动验证 Agent。

其他目标运行环境、测试数据和专用测试账号由项目维护者准备。验证 Agent 不读取真实用户配置，不索取登录凭据，不处理模型服务配置，也不扩大需求范围。

## 安全边界

- 启用 `contextIsolation` 和 Renderer sandbox，禁用 Node integration。
- 所有任务、配置和模型操作经过窄 IPC 接口；拒绝其他窗口来源的配置读取。
- 设计阶段只开放读取、搜索工具并使用计划权限。
- 开发和验证在独立 worktree 自动执行，仍受提示约束、变更审核、固定检查和推送门禁控制。
- 文件删除需要需求正文逐行授权；可疑脚本和未授权删除进入人工审核。
- 不自动合并目标分支、不部署、不写回外部工单。
