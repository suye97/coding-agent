模块边界

这是一款本地桌面应用，不是远程任务服务。飞书负责需求和审批交互，桌面负责观察与配置，主进程持有任务和交付状态。

飞书渠道与附件

feishu.js 通过 @larksuite/channel 接收消息和卡片动作，把标准化输入交给 Workflow。普通需求支持开发和缺陷修复入口；配置了 TAPD 来源后，还能导入匹配群与发送方的卡片，按精确项目名路由。普通群消息受操作人和需求格式约束；显式群与发送方匹配针对 TAPD 导入。

图片需作为同会话中已登记任务卡片的回复，由任务所有者提交。下载后验证 PNG、JPEG 或 WebP，单张上限 8 MiB、每任务至多 8 张且合计不超过 24 MiB，按 SHA-256 去重。Agent 得到经校验的本地图片路径，Renderer 只读附件元数据。入站写库与 outbox 卡片投递相互独立。

React、Preload 与 IPC

左侧队列，右侧过程、方案、验证和交付，设置走独立抽屉。Renderer 通过 window.desktop 调用固定接口；Preload 不暴露通用 IPC。主进程借 dispatch.js 读取本地快照，并发送 tasks:changed 通知。列表另有 5 秒兜底轮询，运行中任务详情每 1.5 秒刷新。

BrowserWindow 启用上下文隔离和 Renderer 沙箱，禁用 Node 集成；配置读写 IPC 显式检查发送窗口。公开配置只返回密钥是否配置，不返回明文。

Runtime 与 Workflow

Runtime.start() 装配 Store、项目目录、附件存储、Git 仓库与 Agent 执行器，先恢复任务，再按开关连接飞书。每秒调度一次：任务 worker 串行推进，通知 publisher 独立运行，各自最多一个在途调用。

配置保存在应用 userData/settings.json；App Secret、API Key 由 Electron safeStorage 加密，留空保留旧值。保存通过主进程校验项目后，重启运行时。baseBranch 是工作树基线；交付目标始终是所配置远端的 master，两者是不同概念。

源码：装配、配置与调度

Agent Utility Process

主进程通过 AgentProcess 发送一次调用所需的模型配置与上下文；Utility Process 封装 Claude Agent SDK 会话以及流式事件采集。设计在原仓库根目录用只读工具运行；开发和独立验证在对应工作树运行。Agent 不持有任务数据库接口，也不替主进程做远端交付裁决。

子进程按需启动，调用以 ID 匹配；取消会中止对应 SDK 查询，子进程退出会让在途调用失败，后续可重新启动。公开正文只取顶层文本增量，最终文本来自 SDK result；工具活动和验证证据走单独事件。SDK 会话 ID 可用于恢复调用，合并候选实测使用新会话。

交付流程

完整需求自动进入设计，无需逐单确认设计方案。「已推送任务分支」和「已交付」是两个不同的事实。

  1. 接收需求

    识别任务类型、项目和有效正文；信息不足就发补充卡片。

    confirm / design_queued

  2. 设计方案

    只读分析范围、风险、验证计划；写入方案版本。

    designing → queued

  3. 开发并提交

    先保存 worktree 意图，再建隔离工作树；开发 Agent 创建本地提交。

    developing → verifying

  4. 审核和验证

    检查真实提交、差异和工作树，运行固定检查；需要时再补操作证据。

    verifying

  5. 推送并合入

    先推同名任务分支，再合入同一远端的 master；回读确认后才完成。

    verifying → delivered

Git 交付：两次远端更新，一次完成判定

任务分支

按需求类型创建 feature/<任务 ID>_YYYYMMDD 或 fix/<任务 ID>_YYYYMMDD。以配置的本地基线提交建立工作树。主进程核验 HEAD、分支和差异；空提交、脏工作树或返工无增量都不能视为完成。推送前核对远端旧值，成功后先持久化任务分支交付记录。

同一远端的 master

目标已包含任务提交则直接确认；可快进则复用已验证提交。若分叉，先生成双父合并提交并保存候选，在隔离工作树对候选重新审查和验证，再核对远端引用并更新。最后回读目标，确认包含候选提交才写入 delivered。

失败不等于回滚任务分支。 合并冲突、远端变化、分支保护或候选验证失败会阻塞交付。若任务分支已推送，记录仍在，重试会重新核对已有提交与证据。应用不会把部署或外部工单回写算作这条链路的一部分。

源码：工作树、主链路与远端引用更新

验证门禁

主进程运行项目已配置的固定检查。只有本次变更直接涉及且缺少自动化覆盖的真实操作行为，才额外要求逐步操作证据。

先审查，再执行

对实际 Git 差异应用删除和高风险变更规则。删除需要正文中的精确路径授权；未授权删除或命中可疑脚本规则需审批。审批绑定具体提交。

先固定检查，再补证据

来自项目配置的可执行文件与参数按顺序运行。检查结束后复核待验提交、分支和工作树，不能用检查过程中改写过的代码作为交付对象。

先验证，后推送

固定检查、适用的操作验证和审批全部满足才推送。分叉产生新合并候选时，不能拿任务分支上的结论直接替代候选检查。

操作证据的复用顺序

  1. 项目的自动化操作报告

    优先采用项目预先配置的 kind: operation 检查报告，由主进程校验是否对应待验任务与步骤。

  2. 开发 Agent 已采集的证据

    复用同一提交上符合要求的操作观察，避免在后置验证阶段重复执行。

  3. 独立验证 Agent 补缺

    先恢复身份匹配的检查点，再只跑缺失步骤。Node / Electron 项目按适用条件在工作树内做依赖和目标 Electron 版本预检。

证据不是模型结论

操作断言和观察须来自同一实际操作程序。证据绑定需求版本、方案版本、提交、基线与完整步骤；Agent 证据包含工具调用 ID 与完整输出 SHA-256。独立截图、普通文件读取和最终一句 passed 都不能替代逐步记录。操作类缺陷还需基线复现，修复后的观察必须与基线不同。

15 分钟整个验证阶段
10 分钟单次独立验证
60 秒等待首个 SDK 协议事件
3 分钟没有模型或工具进展
验证预检与采集实现

有 npm 锁文件的 Node 项目先核对锁文件、依赖指纹及已安装包，缓存失效才重新安装。直接依赖 Electron 时还要探测工作树所需的确切版本，缺失时补齐同版本，不以本机另装的应用或 Electron 替代。版本探测不验证界面行为；预检失败不启动独立验证 Agent。

Utility Process 从 SDK 持久化文件、结构化 stdout 或后台任务输出文件提取观察；同步结果缺少结构化输出时，回退到 SDK 命令结果文本。SHA-256 针对实际读到的证据来源。首个 SDK 事件结束启动计时；活动可重置无进展计时，不能延长单次总预算。15 分钟外层预算还涵盖固定检查、预检、推送和合入。

状态与恢复

SQLite 是任务状态的依据。工作树、提交、检查点和通知映射都有已落盘的身份，重试并不意味着从设计起全部重跑。

条件状态与处理重试时保留什么
项目或正文不足confirm；补充后重新识别，满足条件进 design_queued。任务编号与历史；需求版本变化使旧方案与审批失效。
替代方案manual_review；批准后进入开发队列，拒绝则阻塞。批准绑定需求和方案版本，原需求正文仍保留。
提交需要审批manual_review；批准后进入 verify_queued。只授权被审查的提交，提交有变则重新判断。
检查失败、超时或 Git 异常blocked；记录失败阶段，重试回对应队列。验证失败也可进入返工。匹配当前身份的证据、已推送记录及合并候选可复用。
取消或应用重启取消先写 cancelled 再中止。重启可继续调度排队任务，残留运行态标为中断和阻塞，不自动继续危险写操作。保留任务历史、工作树意图和验证进度；旧版已推送任务不被自动合并。

落盘与读模型

任务与历史

数据库位于数据目录，以飞书 App ID（未配置时用 local）命名，使用 node:sqlite 的 WAL。tasks 存当前态，history 存修订快照；常规状态更新用乐观 revision 核对后写入任务、历史和通知。

事件与通知

events 记录入站去重，outbox 记录待发通知；首次发送复用幂等键，已有卡片按消息 ID 更新。网络失败退避重试。卡片动作还需匹配操作者、任务、消息和当前 revision。

查询与进展

dispatch 只读生成任务摘要和详情。进展可不增加卡片 revision，公开正文独立按调用保存：每任务最近 8 份有正文记录，每份保留末尾约 24,000 字符。

领取：定时器触发，事务决定谁运行

??= 防止重入。 每秒回调时，如果上一次 worker 的 Promise 还在，就不会再次调用 work()；finally 才清空引用。publisher 有独立引用，所以发卡片可以与任务运行重叠。

查运行态和写运行态是同一事务。 inFlight 对应设计中、开发中、验证中。inStage() 用 ORDER BY rowid（src/store.js:83），因此 [next] 取的是三个待执行状态里最早入库的任务，不按状态参数的排列优先。

update(next, kind) 先落盘。 领取时同时生成 attempt ID 并写入运行态；事务成功后才继续执行本轮任务。

推进：先写工作树意图，再执行 Git 操作

intent() 先确定身份。 第一次 persist() 保存仓库、目录、分支和基线意图；prepare() 再创建或核对实际工作树，第二次保存准备结果。如果创建后、写回前中断，重试可按意图核对已有目录。

persist() 拒绝过期状态。 一般写入受取消和验证超时共同约束；afterTimeout 用于记录超时失败，但仍尊重用户取消。数据库的 attempt ID 不同或任务已取消时，旧调用不能写回。

设计阶段成功会增加 planVersion 并返回队列（src/workflow.js:777）；开发结束写入 verifying 后则在本次 work() 中继续（src/workflow.js:826）。

审批：同一个按钮，按审查类型走不同分支

alternative 是范围决定。 保存获批方案及需求、方案版本，回 queued 排队开发，不直接进入验证。

change 是具体提交的决定。 mergeResult ?? result 优先找当前候选结果；只有待审 SHA 同时匹配结果和审查记录，才写 changeReviewApproval 并回 verify_queued。不匹配就返回「审批内容已失效」。

按钮进入此函数前，onAction() 还会核对操作人、任务归属、会话、卡片消息 ID 和 revision（src/workflow.js:478）。

恢复：在途任务先阻塞，再按失败阶段重试

重启不会续跑旧调用。 残留运行态的 attempt 标为 interrupted，原阶段写入 failedStage 后才改成 blocked。已在队列中的任务仍可正常被领取。

重试按失败阶段路由。 例如 verifying 失败只回 verify_queued；能否复用已完成工作由后续的提交、证据和交付记录核对决定。取消则先保存 cancelled，再中止匹配调用（src/workflow.js:467、src/workflow.js:487）。

审查与放行

沿 verifyCommit()、push()、integrate() 的调用顺序，找出哪些判断会停住交付。

  • 提交与差异
  • 固定检查
  • 证据复用
  • 推送与合入

提交与差异：为什么项目命令还没执行就能暂停？

先判断是否有东西可交付。 status 非空、HEAD 等于基线，或返工没有新 SHA 时立即返回失败的 cleanCheck。任务提交还要求实际差异；!candidate 表示不对合并候选套用这一空差异判断。

审查以实际 Git 差异为输入。 任务提交对照基线和已有的上次推送；候选只对照 master 父提交。关闭重命名识别以保留原路径；删除和类型变化进入删除集合，符号链接或脚本规则命中进入警告集合（src/repository.js:153、src/change-review.js:20）。

approvalRequired 不是通用授权。 删除需需求正文逐行授权具体路径；有未授权删除或警告时，只有已批准同一 SHA 才可继续。发现项过多或路径无法安全展示时直接抛错；需审批时，verifyCommit() 写入 manual_review，项目命令尚未执行（src/workflow.js:641）。

固定检查：通过的是命令，还是同一个提交？

project.checks 来自项目配置。 主进程传入可执行文件与参数数组，并用 operationValidation 决定是否执行操作类检查。操作检查拿到当前提交和验证计划，stdout 进入报告列表，而不是直接作为普通日志展示。

matchesWorktree(snapshot) 在每次命令后执行。 HEAD、分支或工作树变化会停止后续命令，清空 operationReports，并让 cleanCheck 失败。普通命令失败会记在 checks；只要有一项没通过，verifyCommit() 就抛错（src/workflow.js:646）。

操作证据：什么情况下可以跳过重复实测？

身份匹配与证据完整是两回事。 evidenceIdentityMatches() 对比 SHA、操作、预期、基线、需求版本、方案版本和有序步骤；completeStoredEvidence() 再查实际观察和工具标识。缺陷任务还要有与修复结果不同的基线观察。

先看项目报告，再看已有证据。 verifyCommit() 优先解析操作检查的报告；没有报告时，才评估开发 Agent 或历史证据。匹配但不全时，恢复已有逐步记录，由独立验证 Agent 补缺（src/workflow.js:647、src/workflow.js:668）。

recordCheckpoint() 不把每条输出都当成完成。 重新计算可接受观察；没新增就只记录近期拒绝诊断，有新增才更新 completedSteps，并立即保存。重试读到的是已核对的进度，不是模型回复里说完成的百分比。

推送与合入：为什么写两次远端，却只完成一次？

task.delivery 是已推送检查点，不是完成状态。 需求和方案版本一致的重试可以跳过推送。首次推送前，push() 还会核对当前 HEAD、任务分支、审查以及远端旧引用（src/repository.js:247）。

fastForward 决定是否需要验证新候选。 目标已包含任务提交就直接确认；可快进则复用已验证 SHA；分叉才核对双父提交，在隔离工作树调用 verifyCandidate。候选检查要求人工审批时返回空值，外层 if (!merged) return 让任务停在待审批。

回读后才写 delivered。 合并时复查源分支与目标旧值，使用以目标旧 SHA 为预期值的更新；再读远端确认包含本轮提交。异常由外层记录为阻塞（src/workflow.js:861），不是撤销已经成功的任务分支推送。

区分规则审查与运行时隔离。 按 SHA 的人工批准不会自动覆盖新合并候选，也不跳过固定检查或实测；正则审查不是完整的安全扫描。

典型分支

用三个例子区分「能继续检查」「能重试合入」和「已经交付」。

  • 提交删除了未授权文件

    approvalRequired 为真，检查在项目命令前暂停。所有者批准后回 verify_queued；若提交变化，旧 SHA 不再匹配。

  • 操作证据差最后一步

    验证中断后，从 completedSteps 恢复匹配的通过记录，只补缺的证据。若运行状态已丢失，仍需重建前置状态；提交或计划一变就重新核验证据身份。

  • 任务分支已推送，合入时目标变化

    refs.read(masterRef) !== base 时合入抛错，任务阻塞。重试读到 task.delivery 时无需重复推送，但仍按最新 master 判断是否需要新候选及复验。
